HMWK 2 — From Wallet Seed to Ethereum Address

Hashing, Key Derivation and Cryptographic Primitives

1The Cryptographic Pipeline Overview

A modern wallet (like MetaMask, Rabby, or Exodus) does not simply generate keys at random, but uses a strict and deterministic cryptographic pipeline to transform a mnemonic sequence of words into a hexadecimal Ethereum address complete with a checksum.

Mnemonic Phrase (e.g. 12-24 words)
↓ BIP-39 (PBKDF2 + HMAC-SHA512) ↓
Root Seed (512-bit)
↓ BIP-32 / BIP-44 (HD Key Derivation) ↓
Private Key (256-bit)
↓ secp256k1 (Elliptic Curve Multiplication) ↓
Public Key (Uncompressed 64-byte)
↓ Keccak-256 (Hashing) ↓
Raw Ethereum Address (20-byte)
↓ EIP-55 (Mixed-case Encoding) ↓
Checksummed Address (0x...)

2In-Depth Analysis of Pipeline Nodes

Below is an in-depth analysis of every single standard and mathematical primitive that makes up the journey from the initial entropy to the public address.

BIP-39: Mnemonic and Seed Generation

  • Initial Entropy: The process begins by generating 128 to 256 bits of pure randomness. A small checksum (derived from SHA-256) is appended to this entropy.
  • Mnemonic Sentence: The resulting bit sequence is split into 11-bit groups. Each group acts as an index (from 0 to 2047) to map a specific word within the standard BIP-39 wordlist. This allows humans to easily write down and remember their backup.
  • Key Stretching (PBKDF2): To convert the words into a usable seed (and to defend against brute-force attacks), the mnemonic phrase is concatenated with an optional salt (defaulting to the string "mnemonic") and passed through the PBKDF2 function using HMAC-SHA512 for 2048 iterations. The result is the 512-bit Root Seed.

BIP-32: Hierarchical Deterministic (HD) Key Derivation

  • The 512-bit Root Seed is split in half: the first 256 bits become the Master Private Key, and the second 256 bits become the Master Chain Code (which serves as additional entropy).
  • BIP-32 defines the mathematics to generate an infinite "tree" of child keys starting from this single master node. This allows the generation of billions of valid addresses from a single initial mnemonic phrase, without the need to back up every newly generated key.

BIP-44: Standard Derivation Paths

  • While BIP-32 defines how to derive keys, BIP-44 defines where to derive them, creating a logical tree formatted as: m / purpose' / coin_type' / account' / change / address_index.
  • For example, for Ethereum, the standard path is m/44'/60'/0'/0/x. The number 60' is the registered coin type for the Ethereum network. By changing only the last parameter (the index), the wallet generates infinite consecutive addresses for the user.

secp256k1: Elliptic Curve Cryptography

  • Once the Private Key (a massive 256-bit integer) is obtained, it is multiplied by the Generator Point (G) on the standardized secp256k1 elliptic curve. The operation is one-way (thanks to the Elliptic Curve Discrete Logarithm Problem, ECDLP).
  • The output is an (X, Y) coordinate on the curve, representing the Public Key. While Bitcoin often uses the compressed format, Ethereum uses the uncompressed 64-byte public key (removing the standard 0x04 prefix).

Keccak-256: Hashing

  • The 64-byte public key is fed into the Keccak-256 hash function. Keccak uses a complex "sponge construction" (absorb and squeeze) to irreversibly mix the data.
  • The output of the Keccak function is a 32-byte (256-bit) string. Ethereum takes only the last 20 bytes (which correspond to 40 hexadecimal characters) of this hash. This truncation becomes the raw Ethereum address.

EIP-55: Mixed-case Checksum Encoding

  • Since raw hexadecimal addresses have no built-in safety mechanisms, a single mistyped character would result in an irreversible loss of funds. Vitalik Buterin introduced EIP-55 to solve this problem without modifying the base protocol.
  • How it works: The raw address (in lowercase) is hashed again with Keccak-256. The algorithm checks every single hexadecimal character of the address: if it is a letter (a-f), it checks the corresponding nibble (half-byte) in the newly calculated hash. If the nibble is >= 8, the letter in the address is capitalized. This creates a unique capitalization pattern. If a user makes a typo, the hash changes drastically and the uppercase/lowercase pattern no longer matches, allowing software (e.g., MetaMask) to block the transaction.

3Crucial Distinctions and Purpose of Primitives

ConceptDefinition & Role
Key Generation & DerivationGeneration is the creation of initial entropy (BIP-39). Derivation (BIP-32/44) is the mathematical logic used to systematically manage an infinity of keys from that seed without having to save anything else.
Public-Key CryptographyGuarantees ownership. By leveraging curve mathematics (secp256k1), it allows a user to sign transactions (proving ownership of the Private Key) without revealing anything to the network other than the Public Key.
HashingHashing (Keccak-256) guarantees one-way determinism. It partially hides the Public Key until a transaction occurs and reduces the 64 bytes to a standard 20-byte format that is easier to process.
Checksums & Encoding(EIP-55). Formatting rules that act exclusively at the software interface level. They prevent human errors (typos) without altering the cryptographic foundations of the Ethereum protocol.

4Historical Context (Temporal Context)

These technologies were not born simultaneously; they are the result of decades of evolution in information theory and cybersecurity:

  • 1977 - RSA: Rivest, Shamir, and Adleman introduce asymmetric public-key cryptography, laying the conceptual foundations for systems like Bitcoin and Ethereum.
  • 2001 - SHA-2 / SHA-512: Standardized by NIST. Very robust, it is used in BIP-39 within the PBKDF2 process to stretch the mnemonic string into the seed.
  • 2012 - BIP-32: Introduced to solve the serious problem of early Bitcoin wallets requiring constant backups every time a new key was generated (JBOK - Just a Bunch Of Keys). Deterministic wallets are born.
  • 2013 - BIP-39: A leap forward for Usability. Replaces impossible-to-remember hexadecimal strings with simple lists of English words.
  • 2014 - BIP-44: Expands BIP-32 to natively support multiple accounts and, above all, multiple coins (Bitcoin, Ethereum, Litecoin) from a single mnemonic phrase, standardizing the derivation tree logic.
  • 2015 - SHA-3 vs Keccak: A fundamental historical distinction. Keccak won the NIST competition to define the SHA-3 standard. However, shortly before finalization, NIST altered the padding parameters (changing from 0x01 to 0x06). Ethereum, which was already in advanced development, decided to keep the original Keccak. This is why "Keccak-256" and "SHA3-256" produce different hashes today.
  • 2016 - EIP-55: An elegant hack introduced after Ethereum's birth to solve frustration (and financial losses) due to typing errors on addresses.

5Why use multiple algorithms instead of just one?

Instead of having a super-algorithm that does everything, the pipeline is segmented because each step solves a specific threat or need that another algorithm couldn't handle efficiently:

  • BIP-39 / BIP-32 / BIP-44: Solve the problem of human management and usability. No elliptic curve alone can structure backups in the form of easily memorable words.
  • secp256k1: Solves the problem of asymmetric authentication. A Hash function doesn't allow Digital Signatures, while the elliptic curve was specifically chosen to allow fast validations and very compact signatures.
  • Keccak-256: Solves problems of privacy and length standardization. Deriving the address from the hash of the public key (instead of directly using the public key) adds a layer of quantum resistance (until it is exposed for the first time).
  • EIP-55: Solves the problem of user interface errors (UI/UX). Cryptographic algorithms work with invisible bits; EIP-55 converts the hash metadata into a visual format (uppercase/lowercase) to defend the user from their own fallibility.
